# ADR 003. Слоистая архитектура backend

## Контекст

Backend обрабатывает запросы к нескольким сущностям (пользователи, звонки,
контакты, очереди). Нужно решить, как организовать код, чтобы его было легко
читать, тестировать и развивать.

## Варианты

1. **Всё в контроллерах** — быстро писать поначалу, но логика и доступ к базе
   смешиваются, код дублируется, тестировать тяжело.
2. **Слоистая архитектура** (`routes → controller → service → repository`) —
   больше файлов, но чёткое разделение ответственности.
3. **Чистая (hexagonal) архитектура** — максимально развязанные слои, но
   избыточна для проекта такого масштаба.

## Решение

Использовать **слоистую архитектуру** с четырьмя слоями у каждой сущности.

## Последствия

**Плюсы:**
- Каждый слой можно понять и протестировать отдельно: сервис — правила
  предметной области, репозиторий — SQL.
- Изменения локализованы. Например, смена базы данных затрагивает только
  репозитории.
- Тесты API проверяют реальное поведение через настоящие HTTP-запросы.

**Минусы и компромиссы:**
- Больше файлов и «церемоний» для простых операций. Это осознанная плата за
  читаемость и сопровождаемость — важнее для проекта, претендующего на
  «middle и выше».

## Структура модуля

Каждая сущность в `modules/<name>/` содержит:

- `<name>.routes.ts` — URL и middleware;
- `<name>.controller.ts` — перевод HTTP ↔ вызов сервиса;
- `<name>.service.ts` — бизнес-логика;
- `<name>.repository.ts` — SQL;
- `<name>.schema.ts` — схемы валидации (Zod).
