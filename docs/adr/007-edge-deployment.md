# 007. Публикация демо на Cloudflare Workers

## Контекст

Основная версия проекта рассчитана на запуск «у себя»: Node.js-сервер (Express)
и база SQLite-файл. Это правильно для разработки и для показа инженерных
решений, но такой сервер **нельзя просто открыть по публичной ссылке** — нужен
хостинг, на котором живёт долгоживущий процесс Node.js.

Для отклика на вакансию полезно дать рекрутеру работающую ссылку, а не только
исходники. Значит, нужна площадка, где демо поднимется быстро, бесплатно и без
администрирования сервера.

## Варианты

1. **VPS / облачная виртуалка (Node + PostgreSQL).** Полный контроль, но нужны
   настройка ОС, домен, HTTPS, обновления и оплата. Для демо — избыточно.
2. **PaaS (Railway, Render, Fly.io).** Проще VPS, но тоже нужен постоянный
   контейнер, а бесплатные тарифы «засыпают» и холодно стартуют.
3. **Cloudflare Workers + D1.** Serverless-функции на edge-сети + serverless
   SQLite. Нет сервера как такового, платить за простой не нужно, HTTPS и
   глобальная сеть — из коробки.

## Решение

Выбран **Cloudflare Workers + D1**. Но есть принципиальное ограничение:
Worker — это НЕ Node.js. Там нет файловой системы, нет долгоживущих процессов и
нет модуля `node:sqlite`, на котором построен основной backend.

Поэтому написан **edge-двойник бэкенда** — папка `worker/`. Это тот же самый
REST-API с теми же путями, форматами ответов и ролями, но:

- вместо Express — нативный роутинг Worker по сегментам пути (`worker/index.ts`);
- вместо `node:sqlite` — база **D1** (`env.DB`), это тоже SQLite, но управляемый
  Cloudflare;
- вместо `bcrypt` (нативный модуль) — **PBKDF2 через Web Crypto** (`worker/lib/crypto.ts`);
- вместо jsonwebtoken — собственная подпись **HS256 через Web Crypto**;
- та же схема таблиц и те же демо-данные (`worker/db.ts`), те же права доступа
  (`requireRole`).

Фронтенд при этом **меняется ноль раз**: он общается с `/api/...`, а формат
ответов `{data, meta}` / `{error:{code,message}}` полностью совпадает. Это и
есть главный выигрыш выбранной архитектуры — фронтенд не знает и не должен
знать, какой backend под ним.

## Последствия

**Плюсы:**

- Рабочая публичная ссылка без сервера и оплаты простоя.
- Демонстрирует умение адаптировать архитектуру под ограничения платформы, а не
  ломать её: два взаимозаменяемых бэкенда за одним контрактом API.
- Фронтенд остаётся единым источником правды для UI.

**Минусы и ограничения (честно):**

- **Дублирование API-логики.** Логика теперь в двух местах (Node и Worker) и
  должна развиваться синхронно. Для демо это приемлемый компромисс; в реальном
  продукте так нельзя — там общий слой доступа к данным или единый источник.
- **База демо-версии — отдельная D1.** Это не та же база, что при локальном
  запуске. Данные для показа генерируются при первом запросе
  (`ensureReady` — ленивое развёртывание).
- **Лимиты платформы.** CPU-время запроса на бесплатном тарифе ограничено;
  тяжёлые операции (массовый экспорт, длинные отчёты) сюда не поместятся.
- **Пароли в демо хэшируются PBKDF2**, а не bcrypt — это осознанная замена
  нативного модуля на Web Crypto, совместимую с edge-средой.

## Когда это стоит пересмотреть

Если проект станет продуктовым, правильнее держать **один** backend на
Node/SQL (или перенести всё на edge целиком, включая фронтенд-сборку). Дублировать
бизнес-логику на двух платформах долго не получится — расхождения неизбежны.

## Как повторить деплой

```powershell
# 1. Собрать фронтенд (он попадает в образ Worker как статика)
npm --workspace frontend run build

# 2. Указать доступы Cloudflare и выложить
$env:CLOUDFLARE_API_TOKEN="<ваш токен>"
$env:CLOUDFLARE_ACCOUNT_ID="<ваш account id>"
npx wrangler deploy
```

Конфигурация — в `wrangler.jsonc` (привязка D1 `DB`, статика `ASSETS`,
переменные окружения в `vars`). Создание базы: `wrangler d1 create voxdesk`.
