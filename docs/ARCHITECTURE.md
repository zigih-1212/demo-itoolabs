# Архитектура VoxDesk

Документ объясняет, **как** устроен проект и **почему** приняты такие решения.
Он рассчитан на человека, который видит код впервые.

---

## Общая картина

```
Браузер (SPA на Vue)
        │  HTTP / JSON  (/api/...)
        ▼
Backend (Express)
        │  SQL
        ▼
SQLite (файл на диске)
```

Frontend — одностраничное приложение: после первой загрузки оно общается с
сервером только данными (JSON), а не новыми страницами. Backend — REST API:
каждый адрес (`/api/calls`, `/api/users`) отвечает за свою сущность.

---

## Backend: слоистая архитектура

Запрос проходит строго по слоям — у каждого ровно одна ответственность.
Это упрощает тестирование и изменение: правка в одном слое не ломает другие.

```
HTTP-запрос
   │
   ▼
routes        — сопоставляет URL с контроллером, навешивает middleware
   │
   ▼
middleware    — проверка авторизации, роли, валидация данных
   │
   ▼
controller    — принимает запрос, вызывает сервис, формирует ответ
   │
   ▼
service       — бизнес-логика: правила, проверки, вычисления
   │
   ▼
repository    — единственное место, где выполняются SQL-запросы
   │
   ▼
SQLite
```

### Зачем столько слоёв?

- **routes** знают только про URL и middleware — их легко читать.
- **controller** не содержит бизнес-логики: он «переводит» HTTP в вызов
  сервиса и обратно. Так логику можно вызвать и из теста, и из другого места.
- **service** — «мозг». Здесь правила: например, «нельзя удалить себя»,
  «email должен быть уникальным». Тесты проверяют именно эту логику.
- **repository** изолирует SQL. Если завтра сменить SQLite на PostgreSQL,
  менять придётся только здесь, а не во всём проекте.

### Структура папок backend

| Папка | Ответственность |
| --- | --- |
| `config/` | Чтение переменных окружения и их проверка через Zod |
| `db/` | Схема таблиц, подключение, миграции, наполнение данными |
| `domain/` | Типы предметной области (User, Call, Queue…) |
| `lib/` | Переиспользуемые утилиты: логи, классы ошибок, работа с токенами |
| `middleware/` | Проверки до контроллера: auth, роли, валидация, ограничение частоты |
| `modules/` | По папке на сущность: routes, controller, service, repository, schema |

## Единый формат ответов API

Любой эндпоинт отвечает по одному шаблону — клиенту не нужны особые случаи.

**Успех:**
```json
{ "data": { ... }, "meta": { "total": 42, "page": 1, "limit": 20, "pages": 3 } }
```

**Ошибка:**
```json
{ "error": { "code": "VALIDATION_ERROR", "message": "…", "details": { "email": ["…"] } } }
```

Коды ошибок: `VALIDATION_ERROR` (400), `UNAUTHORIZED` (401), `FORBIDDEN` (403),
`NOT_FOUND` (404), `CONFLICT` (409), `RATE_LIMITED` (429), `INTERNAL_ERROR` (500).

Все ошибки проходят через один обработчик (`middleware/error.middleware.ts`),
поэтому формат одинаков везде, а в продакшене детали внутренних ошибок не
утекают наружу.

## Безопасность

- **Пароли** хранятся только в виде хэша (bcrypt). Открытый пароль нигде не
  сохраняется.
- **Вход по токенам**: краткоживущий *access*-токен (JWT) для запросов и
  долгоживущий *refresh*-токен (в httpOnly-куке) для продления сессии.
  Refresh-токен хранится в базе в виде хэша и **ротируется** при каждом
  обновлении — украденным токеном нельзя пользоваться бесконечно.
- **Права** проверяются на сервере: `requireRole('admin')` и подобные
  middleware. Клиент лишь скрывает кнопки, но реальная защита — на backend.
- **Защита от перебора**: ограничение частоты запросов (`express-rate-limit`)
  отдельно для входа/регистрации и отдельно для остального API.
- **Заголовки безопасности**: `helmet`.
- **Валидация входа**: все данные проверяются схемами Zod до попадания в
  логику. Неверный запрос отклоняется с понятным описанием.

## Frontend: слоистая архитектура

```
views (страницы)
   │  читают/меняют
   ▼
stores (Pinia)  ── вызывают ──►  api (слой запросов)
   │                                   │
   ▼                                   ▼
components (UI)                    http.ts (fetch)
```

| Папка | Ответственность |
| --- | --- |
| `api/` | Типизированные функции запросов к backend |
| `stores/` | Состояние экрана: данные, загрузка, фильтры (Pinia) |
| `views/` | Страницы: композиция компонентов и связь со store |
| `components/` | Переиспользуемый UI (кнопки, поля, таблицы, графики) |
| `composables/` | Переиспользуемая логика (например, диалог подтверждения) |
| `router/` | Маршруты и проверка доступа |
| `styles/` | Дизайн-токены, миксины, базовые стили |
| `utils/` | Форматирование дат/телефонов/чисел, словари подписей |

### Почему так

- Страницы **не делают запросы напрямую** — только через store. Так состояние
  централизовано, а запрос легко замокать в тесте.
- **Дизайн-токены** (`styles/_tokens.scss`) описывают цвета, отступы,
  типографику в одном месте. Это и есть зачаток дизайн-системы: изменить
  тему можно, не трогая компоненты.
- Компоненты **доступны с клавиатуры**: у интерактивных элементов есть
  видимый фокус, у форм — связанные подписи и объявление ошибок для
  скринридеров.

## Аутентификация «в двух словах»

1. Пользователь входит → сервер выдаёт пару токенов.
2. Access-токен клиент прикладывает к каждому запросу (заголовок
   `Authorization: Bearer …`).
3. Когда access-токен истекает, клиент молча обновляет его refresh-токеном.
4. Если и refresh-токен недействителен — пользователя отправляют на вход.

Эта логика собрана в `frontend/src/api/http.ts`, поэтому повторы и обновление
токена не нужно писать в каждой функции API.

## Тестирование

Backend покрыт тестами (auth, users, contacts, calls, очереди, аналитика).
Тесты поднимают настоящий Express-приложение и обращаются к нему как клиент
(`supertest`), проверяя реальные ответы — статусы, тела, права доступа.

Запуск: `npm test --workspace @voxdesk/backend`.

## Куда развивать дальше

- Заменить SQLite на PostgreSQL — правится только `db/` и репозитории.
- Вынести модули в отдельные сервисы — границы уже проведены по модулям.
- Добавить WebSocket для «живой» очереди звонков.
- Подключить реальную телефонию (SIP) вместо демо-данных.
